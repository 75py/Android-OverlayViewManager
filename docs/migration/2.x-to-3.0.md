# Migrating from 2.x to 3.0.0

3.0.0 is a breaking API update and is currently unreleased. This guide uses the final API; temporary deprecated bridges in the development branch are not migration targets.

## Migration checklist

1. Raise the application's minimum supported API to 23 or later and use a compatible build toolchain.
2. Initialize `OverlayViewManager` once from `Application.onCreate()` on the main thread.
3. Choose an Activity or application owner for each handle. Do not retain Activity contexts in application overlays.
4. Replace mutable fluent calls with an immutable `OverlaySpec`, and handle every operation's `OverlayResult`.
5. Move permission UI to the host and recheck permission after returning from Settings.
6. Implement explicit disposal and failure handling. Keep an application handle if removal fails.
7. Update Timber integration and test your actual devices, window configurations, and touch targets.

## API replacements

| 2.x pattern | 3.0.0 replacement |
| --- | --- |
| `overlay.setWidth(...).setX(...).setAlpha(...)` | Pass `OverlaySpec` at creation, or call `update(newSpec)`. Kotlin: `copy`; Java: `toBuilder().setX(...).build()`. |
| `overlay.update()` | `overlay.update(spec)` returns a result and synchronously applies or stores configuration. |
| Chained `show()` / `hide()` calls | Read the returned `OverlayResult`; keep the handle separately. |
| `isVisible()` | `state == OverlayState.ATTACHED` (Java: `getState()`). This reports attachment, not visual occlusion. |
| `getX()` / `getY()` on the handle | `spec.x` / `spec.y` (Java: `getSpec().getX()` / `getY()`). |
| `setTouchable` / `setDraggable` | Select `PASS_THROUGH`, `INTERACTIVE` or `DRAGGABLE` in `OverlaySpec.touchMode`. |
| `overlay.setOnClickListener(...)` | `overlay.view.setOnClickListener(...)` (Java: `getView()`). |
| A custom public drag listener | Use `DRAGGABLE`; internal drag machinery is not a public extension API. |
| `allowViewToExtendOutsideScreen` | `OverlaySpec.allowOutsideBounds`; no system-bar placement guarantee. |
| `setScreenBrightness(...)` | `OverlaySpec.screenBrightness` on an Activity overlay only. |
| `manager.canDrawOverlays()` | `manager.overlayPermission().isGranted(context)` or a standalone `OverlayPermission`. |
| `requestOverlayPermission` / `showPermissionRequestDialog` | Host-owned rationale and Activity Result launch of `settingsIntent(context)`, followed by a fresh permission check. |
| `getDisplayWidth()` / `getDisplayHeight()` | Read the target host window's bounds and insets with a compatible fallback. |
| Dropping a reference after hiding | Explicitly `dispose()`; discard the sole application handle only after success. |

Ordinary Android View methods such as `View.setAlpha()` and `View.setOnClickListener()` remain Android APIs. The migration removes the old methods on the overlay handle, not methods on every object with the same name.

## Configuration in Java and Kotlin

Java uses a builder and explicitly keeps the handle:

```java
TextView label = new TextView(activity);
label.setText("Activity overlay");
OverlaySpec spec = new OverlaySpec.Builder()
        .setTouchMode(OverlayTouchMode.DRAGGABLE)
        .setX(24)
        .setY(48)
        .build();
OverlayView<TextView> handle = OverlayViewManager.getInstance()
        .newOverlayView(label, activity, spec);
OverlayResult shown = handle.show();
if (!shown.isSuccess()) {
    Log.w("Overlay", "Show failed: " + shown.getFailure(), shown.getCause());
}
```

Kotlin uses defaults and immutable copies:

```kotlin
val label = TextView(activity).apply { text = "Activity overlay" }
val handle = OverlayViewManager.getInstance().newOverlayView(
    label, activity, OverlaySpec(touchMode = OverlayTouchMode.DRAGGABLE),
)
val shown = handle.show()
if (!shown.isSuccess) Log.w("Overlay", "Show failed: ${shown.failure}", shown.cause)
val moved = handle.update(handle.spec.copy(x = 24, y = 48))
if (!moved.isSuccess) Log.w("Overlay", "Move failed: ${moved.failure}", moved.cause)
```

These fragments run on the main thread; their owner retains `handle` for later hiding or disposal. In Java, updating a single field is `handle.update(handle.getSpec().toBuilder().setX(24).build())`.

## Results, state, and retry

`OverlayResult` exposes `state`, `changed`, `failure`, `cause` and `isSuccess`. In Java use `getState()`, `getChanged()`, `getFailure()`, `getCause()` and `isSuccess()`. Use the classified failure for recovery instead of parsing exception text.

- `CONFIGURED`: reusable, currently not attached. A successful `hide()` returns here.
- `ATTACHED`: attached according to the handle. Another window or OS policy may still hide it visually.
- `DISPOSED`: resources released. Repeated hide/dispose is harmless; create a new handle to show again. Reading `view` after disposal throws.

A recoverable show/update rejection preserves the effective configuration and relevant state. Examples include permission denial, an invalid window token, and opacity admission failure. External detachment can reconcile the state to `CONFIGURED`; use the returned state. `changed == false` alone is not a failure signal: successful no-ops also return false. Inspect `isSuccess` first.

Application `show()` checks permission before attaching. Updates to an attached window rely on the platform's result rather than repeating a permission preflight; a SecurityException is classified as `PERMISSION_DENIED`. Hiding or disposing does not launch permission UI or request a grant.

After a failed application-overlay disposal, keep the handle, owner and retry path. Do not null the field in a `finally` block. Explicit Activity disposal is also retryable, but the final Activity-destruction safety net releases references after one removal attempt regardless of its outcome. Invalid specs, invalid ownership arguments, and off-main-thread calls remain programming errors that can throw.

## Application overlay and permission return

An application overlay needs `SYSTEM_ALERT_WINDOW` in the manifest. The host owns its lifetime; a permission Activity must not be its sole owner. For example, put the following owner in your Application or an appropriately managed service. This Kotlin class uses an Application context and retains the handle after failed removal:

```kotlin
class ApplicationOverlayOwner(private val app: Application) {
    private var handle: OverlayView<TextView>? = null

    fun show(): OverlayResult {
        val current = handle ?: OverlayViewManager.getInstance().newOverlayView(
            TextView(app).apply { text = "Application overlay" },
            OverlaySpec(touchMode = OverlayTouchMode.DRAGGABLE),
        ).also { handle = it }
        return current.show()
    }

    fun dispose(): OverlayResult? {
        val current = handle ?: return null
        val result = current.dispose()
        if (result.isSuccess) handle = null
        return result
    }
}
```

Call both methods on the main thread, inspect their results, and keep this owner reachable until disposal succeeds. Construct it after manager initialization. An Application-owned object is not a background execution guarantee; a long-running use case still needs host-managed Android lifecycle/service behavior.

In the permission Activity, the following Kotlin members consume one explicit user show request. `owner` is the longer-lived owner above, obtained from your Application/service. `showButton` and `closeButton` are your UI controls; do not store the Activity in the owner.

```kotlin
private val permission = OverlayPermission()
private var showRequested = false
private val settingsLauncher = registerForActivityResult(
    ActivityResultContracts.StartActivityForResult(),
) {
    val requested = showRequested
    showRequested = false
    if (requested && permission.isGranted(this)) showOwnedOverlay()
}

private fun requestShow() {
    if (permission.isGranted(this)) {
        showRequested = false
        showOwnedOverlay()
    } else if (!showRequested) {
        showRequested = true
        try {
            settingsLauncher.launch(permission.settingsIntent(this))
        } catch (failure: ActivityNotFoundException) {
            showRequested = false
            Log.w("Overlay", "Overlay permission settings are unavailable", failure)
        }
    }
}

private fun showOwnedOverlay() {
    val result = owner.show()
    if (!result.isSuccess) Log.w("Overlay", "Show failed: ${result.failure}", result.cause)
}

private fun requestClose() {
    showRequested = false
    val result = owner.dispose() ?: return
    if (!result.isSuccess) Log.w("Overlay", "Close failed: ${result.failure}", result.cause)
}
```

Call `requestShow()` from the show button and `requestClose()` from the close button. Register the launcher during Activity initialization, not inside the button listener. After recreation this minimal example forgets the request and requires another user action; it never displays an overlay solely because Settings returned. A host that preserves pending UI requests can save and restore that flag, but must consume it once and allow cancellation. Denial causes no loop and no automatic retry. A grant can be revoked before `show()`, so the result check remains necessary.

For Java, the same flow uses `registerForActivityResult(new ActivityResultContracts.StartActivityForResult(), result -> { ... })`, `permission.isGranted(this)` and `permission.settingsIntent(this)`. See the compiled [sample](../../sample/) for the Java permission flow and application overlay lifecycle.

## Geometry, touch, and screen brightness

`OverlaySpec` holds window dimensions, gravity, offsets, margins, alpha and touch policy. Width/height accept nonnegative values, `MATCH_PARENT` or `WRAP_CONTENT`; normalized margins, alpha and optional brightness must be finite and between 0 and 1. Read bounds from the target window, accounting for insets and RTL. Host UI limits must work without an overlay grant. `allowOutsideBounds` does not override Android's protected display areas.

`PASS_THROUGH` and `WHEN_SYSTEM_ALLOWS` are separate decisions. The former makes this overlay non-touchable; the latter requests cross-UID pass-through where the platform allows it. It is not a promise that touches reach another application. The library's managed opacity admission considers its registered pass-through overlays; it cannot account for every unrelated window on the device. Handle `PASS_THROUGH_OPACITY_EXCEEDED` and `PASS_THROUGH_UNSUPPORTED` explicitly.

Set `screenBrightness` only in an Activity overlay's spec. For example, Java uses `new OverlaySpec.Builder().setScreenBrightness(0.5f).build()` with `newOverlayView(view, activity, spec)`. Kotlin uses `OverlaySpec(screenBrightness = 0.5f)`. Application-scope brightness is rejected.

## Threading and Timber

Manager initialization/access, handle factories, operations, and `view`/`spec` reads require the main thread. `state` and `lastFailure` are thread-safe reads, but reading them separately is not a combined atomic snapshot. `OverlayPermission` is immutable and thread-safe.

Timber logging accepts arbitrary threads and keeps a bounded buffer. Initialize the manager first, call `DebugOverlayTree.init(app)`, plant the returned tree once, and register participating Activities. `setMaxLines` requires at least 1. Same-Application init is idempotent; a different Application while initialized throws. Call `dispose()` on the main thread. On failure retain the tree and retry only in response to a host action; on success `Timber.uproot(tree)` is the host's responsibility. Successful disposal clears callbacks, caches and the buffer, and invalidates old queued renders. Initialization afterward creates a fresh generation.

## Release checks

The repository currently uses JDK 17, SDK 36, Gradle 9.4.1 and AGP 9.2.1 with built-in Kotlin. Do not add a separate Kotlin Android plugin to these Android modules as part of migration. Final 3.0.0 artifact coordinates, version metadata and Java/Kotlin artifact-consumer verification are a later release gate. Device tests, including edge-to-edge positioning and cross-UID touch delivery, remain release-blocking; local unit tests do not replace them.
