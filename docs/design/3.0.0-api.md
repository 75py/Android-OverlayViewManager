# OverlayViewManager 3.0.0 API design proposal (T01)

Status: **proposal — not a public API commitment until Codex and Claude coordinators approve it bilaterally.**

This document is the Codex-side T01 proposal.  It deliberately specifies externally observable behavior, not the internal class layout.  T04--T09 may refine implementation details but must not change these contracts without reopening this proposal.

## Evidence and scope

### Facts observed in the 2.x tree

* `OverlayViewManager` is a process singleton initialized by `init(Application)`.  Its two factories create an application-scoped or an activity-scoped `OverlayView`; only the latter forces `TYPE_APPLICATION`.
* `OverlayView.show()`, `update()`, and `hide()` synchronously mutate `isVisible`, but `OverlayWindowManager` may post the corresponding `WindowManager` call to main and catches every exception.  Thus `isVisible == true` can mean neither that `addView` succeeded nor that it has run.
* The mutable `WindowManager.LayoutParams` object is shared between the caller and a posted operation.  A background `show()` followed by a main-thread `hide()` can execute as `remove` before `add`, and then leave a window attached.
* `ScreenMonitor` itself is a permission-requiring application overlay.  Dragging an activity-scoped overlay can therefore require system-overlay permission, and toggling `setDraggable(false)` before `hide()` leaks a monitor request.
* `OverlayWindowManager.activityInstances` is a `WeakHashMap`, but its value contains an activity window manager.  Its actual reachability must be verified in T08 rather than inferred from the weak key.  The current `DebugOverlayTree` also mutates an `ArrayList` and a `TextView` directly from Timber's arbitrary logging thread.
* Existing public surface includes `OverlayView`, `DraggableOnTouchListener`, permission dialog/launcher helpers, and size accessors; opt-timber publishes `DebugOverlayTree`.  The lint rule specifically identifies `allowViewToExtendOutsideScreen`.

### Non-goals

3.0 does not add Compose APIs, background-service management, a system-wide accessibility overlay, automatic permission prompting, or automatic retry.  An application overlay may outlive an Activity, but the host app remains responsible for foreground-service, background-start, and Play-policy compliance.

## Decision: one synchronous main-thread contract

**Proposed decision:** public API calls which create/configure a handle or mutate its window are `@MainThread`.  The four mutating window operations (`show`, `update`, `hide`, and `dispose`) perform one complete `WindowManager` operation before returning an `OverlayResult`; they never enqueue a later show/hide/update.  Factories and read-only accessors return their declared object/value, not an `OverlayResult`; `OverlayPermission` is immutable and may be queried from any thread.  `OverlayResult` represents recoverable platform failures, while invalid arguments and calls from a non-main thread throw `IllegalArgumentException` or `IllegalStateException`.

| Candidate | Benefit | Failure mode / cost | Decision |
| --- | --- | --- | --- |
| Main-thread-only synchronous calls | Operation order, attachment state, and result are observable together; simple JUnit/Robolectric and device tests; no stale posted work | Callers must switch from worker threads to main | **Adopt** |
| Public serialized async queue | Could accept worker calls | Needs futures/cancellation, a defined queue-drain state, snapshots, ordering semantics, and a way to report failures after return; easily recreates the present show/hide race | Reject for 3.0 |

The library must use `Looper.getMainLooper()` identity, not merely a lock or `synchronized`, to enforce this.  A later main-executor convenience is deliberately not part of 3.0; applications can use their own main executor.  `state` and `lastFailure` are thread-safe read-only exceptions and may be read in every state, including `DISPOSED`; the effective immutable `spec` is read-only but remains `@MainThread`, including after disposal, and `view` remains main-thread-only.  `DebugOverlayTree` is the narrow exception: Timber invokes `log()` on arbitrary threads, so it owns a private, bounded buffer and coalesces rendering onto main without exposing overlay operations off-main.

## Proposed public API

Names below are signatures and contracts, not source code. Kotlin-facing names use idiomatic properties where harmless; the compiled API must expose the Java forms shown as well.

```kotlin
class OverlayViewManager private constructor(application: Application) {
    companion object {
        @JvmStatic @MainThread fun init(application: Application)
        @JvmStatic @MainThread fun getInstance(): OverlayViewManager
    }

    fun <T : View> newOverlayView(view: T, spec: OverlaySpec = OverlaySpec()): OverlayView<T>
    fun <T : View> newOverlayView(view: T, activity: Activity,
                                  spec: OverlaySpec = OverlaySpec()): OverlayView<T>
    fun overlayPermission(): OverlayPermission
}

class OverlayView<T : View> {
    @get:MainThread val view: T // throws after disposal
    val state: OverlayState // readable in every state
    val lastFailure: OverlayFailure? // readable in every state; no retained Throwable
    @get:MainThread val spec: OverlaySpec // effective immutable spec; Java getSpec(), readable on main in every state
    @MainThread fun show(): OverlayResult
    @MainThread fun update(spec: OverlaySpec): OverlayResult
    @MainThread fun hide(): OverlayResult
    @MainThread fun dispose(): OverlayResult
}

enum class OverlayState { CONFIGURED, ATTACHED, DISPOSED }
enum class OverlayScope { ACTIVITY, APPLICATION }
enum class OverlayTouchMode { PASS_THROUGH, INTERACTIVE, DRAGGABLE }
enum class CrossUidPassThrough { SAME_UID_ONLY, WHEN_SYSTEM_ALLOWS }
enum class OverlayFailure { PERMISSION_DENIED, ACTIVITY_DESTROYED, INVALID_WINDOW_TOKEN,
    WINDOW_MANAGER_REJECTED, ALREADY_HAS_PARENT, NOT_ATTACHED,
    PASS_THROUGH_OPACITY_EXCEEDED, PASS_THROUGH_UNSUPPORTED }

class OverlayResult {
    val state: OverlayState
    val changed: Boolean
    val failure: OverlayFailure? // null on success/no-op
    val cause: Throwable? // diagnostic only; null for preflight failures with no exception
    val isSuccess: Boolean
}
```

The shipped Kotlin source retains the established `OverlayViewManager` / `OverlayView` class names, and has explicit Java-friendly overloads for both established factory shapes, with and without a spec.  Java callers must be able to write the following without Kotlin types, coroutines, or `Result`:

```java
OverlayViewManager.init(application);
OverlayViewManager manager = OverlayViewManager.getInstance();
OverlayView<TextView> overlay = manager.newOverlayView(
        new TextView(application),
        new OverlaySpec.Builder().setTouchMode(OverlayTouchMode.INTERACTIVE).build());
OverlayResult result = overlay.show();
if (!result.isSuccess()) {
    // Show the host application's permission rationale or recover its Activity state.
}
```

The manager declares these four Java factory overloads explicitly; Java does not depend on Kotlin default arguments:

```java
public <T extends View> OverlayView<T> newOverlayView(T view);
public <T extends View> OverlayView<T> newOverlayView(T view, OverlaySpec spec);
public <T extends View> OverlayView<T> newOverlayView(T view, Activity activity);
public <T extends View> OverlayView<T> newOverlayView(T view, Activity activity, OverlaySpec spec);
```

`OverlayViewManager.init` is idempotent only for the same `Application` object.  Passing a different `Application` is an `IllegalStateException`; it must not replace process-level window or lifecycle state.  `getInstance` before initialization is an `IllegalStateException`.  Initialization, factory creation, and all mutating handle methods are main-thread calls, so a view and its listener are never configured concurrently with attachment.

### `OverlaySpec`

`OverlaySpec` is immutable and value-based.  Its public Kotlin declaration is:

```kotlin
data class OverlaySpec(
    val width: Int = ViewGroup.LayoutParams.WRAP_CONTENT,
    val height: Int = ViewGroup.LayoutParams.WRAP_CONTENT,
    val gravity: Int = Gravity.TOP or Gravity.START,
    val x: Int = 0,
    val y: Int = 0,
    val horizontalMargin: Float = 0f,
    val verticalMargin: Float = 0f,
    val alpha: Float = 1f,
    val touchMode: OverlayTouchMode = OverlayTouchMode.PASS_THROUGH,
    val crossUidPassThrough: CrossUidPassThrough = CrossUidPassThrough.SAME_UID_ONLY,
    val allowOutsideBounds: Boolean = false,
    val screenBrightness: Float? = null,
) {
    init {
        validate()
    }
}
```

`Gravity.TOP or Gravity.START` is resolved at attachment using the view's current layout direction.  The generated Kotlin `copy(...)` calls the primary constructor, so the same validation applies to direct construction and every copied value.  Java uses this explicit nested builder surface and the value's `toBuilder()`:

```java
public static final class Builder {
    public Builder();
    public Builder(OverlaySpec source);
    public Builder setWidth(int width);
    public Builder setHeight(int height);
    public Builder setGravity(int gravity);
    public Builder setX(int x);
    public Builder setY(int y);
    public Builder setHorizontalMargin(float margin);
    public Builder setVerticalMargin(float margin);
    public Builder setAlpha(float alpha);
    public Builder setTouchMode(OverlayTouchMode touchMode);
    public Builder setCrossUidPassThrough(CrossUidPassThrough mode);
    public Builder setAllowOutsideBounds(boolean allowOutsideBounds);
    public Builder setScreenBrightness(Float brightness);
    public OverlaySpec build();
}

public Builder toBuilder();
```

All Kotlin constructor parameters have defaults, providing the no-argument default construction path.  Builder setters/build, direct `OverlaySpec(...)`, generated `copy(...)`, and `toBuilder().build()` all enforce the same validation: `alpha` and margins are 0..1, dimensions are valid `ViewGroup.LayoutParams` constants or non-negative, and a brightness override is 0..1.  Defaults are `WRAP_CONTENT`, top-start gravity, `(0, 0)` offsets, alpha `1f`, `PASS_THROUGH`, `SAME_UID_ONLY`, `allowOutsideBounds == false`, and no screen-brightness override.  It contains only:

* width, height, gravity, x/y offsets, horizontal/vertical margin, and alpha;
* `OverlayTouchMode`;
* for application `PASS_THROUGH`, `CrossUidPassThrough` (`SAME_UID_ONLY` by default, or the explicit `WHEN_SYSTEM_ALLOWS` opt-in described below);
* `allowOutsideBounds` (default false), which means only normal layout positioning.  It **does not** promise drawing above system bars or navigation controls;
* an activity-only optional screen brightness override (`screenBrightness`), rejected when used with an application-scoped factory.

Builder values are range-checked (`alpha` and margins are 0..1; dimensions are valid `ViewGroup.LayoutParams` constants or non-negative).  `DRAGGABLE` implies an interactive window and uses the library listener; a custom `DraggableOnTouchListener` is not part of 3.0 public API.  Every overlay mode always includes `FLAG_NOT_FOCUSABLE`; `INTERACTIVE` and `DRAGGABLE` omit only `FLAG_NOT_TOUCHABLE`, so neither mode can acquire window focus or an IME target.  The listener consumes a drag only after touch slop, preserves ordinary click delivery otherwise, restores visual state for UP and CANCEL, uses the active window's insets/coordinates, and does not add a second monitor window.

`OverlaySpec` is the primary 3.0 configuration surface.  The current fluent layout/touch setters and no-argument `update()` cannot retain their present meaning because they mutate an in-flight `LayoutParams`; they are removed rather than silently becoming asynchronous.  The `OverlayView` name, both `newOverlayView` factory names, `getView`, `getSpec`, and the existing static manager initialization names are retained to minimize source migration.  `getSpec()` returns the current effective immutable specification rather than the original factory/update input and is a main-thread read, including after disposal: a successful drag updates its x/y values after the corresponding layout update succeeds.  `update(spec)` compares its input to that effective spec (including a dragged position), creates and applies a private snapshot only when unequal, and never exposes `WindowManager.LayoutParams`.

The application scope always uses the platform-supported application overlay type on API 26+ and the supported legacy type only on retained lower API levels.  The activity scope uses the activity's token/application window and must not use an application-overlay type.  3.0 never selects privileged `TYPE_SYSTEM_ERROR`/`TYPE_SYSTEM_OVERLAY`; `allowOutsideBounds` is not an authorization bypass.  Insets, display cutouts, rotation, RTL, multi-window, and Android 15+ edge-to-edge are observable layout constraints rather than an undocumented "status bar height" adjustment.

### Application pass-through and the Android 12 opacity budget

`PASS_THROUGH` means the overlay uses `FLAG_NOT_TOUCHABLE`; it does **not** promise that another UID receives the touch.  On Android 12+ a `TYPE_APPLICATION_OVERLAY` is untrusted, and the system may block a touch through it unless the per-UID opacity conditions are satisfied.  Android documents both the runtime maximum (`InputManager.getMaximumObscuringOpacityForTouch()`) and the combined-opacity formula `1 - product(1 - alpha_i)`. [WindowManager.LayoutParams reference](https://developer.android.com/reference/android/view/WindowManager.LayoutParams), [InputManager reference](https://developer.android.com/reference/android/hardware/input/InputManager)

The default `SAME_UID_ONLY` is intentionally conservative: it supports an application overlay being non-touchable while the host application's own window is below it, but makes no cross-UID delivery claim.  In particular, a default-alpha (`1f`) application overlay is allowed in this mode but must be documented as unsuitable for reliable pass-through to another app.

For cross-UID use, callers must set `CrossUidPassThrough.WHEN_SYSTEM_ALLOWS`.  On API 31+ the library obtains the system maximum on every `show`/`update` that changes an application pass-through handle and maintains a conservative per-manager budget across **all attached library-managed application pass-through handles of this UID**, not just bounds it thinks overlap.  The requested operation is rejected before `addView`/`updateViewLayout` with `PASS_THROUGH_OPACITY_EXCEEDED` when the combined value would exceed the system maximum; a default `alpha == 1f` therefore normally fails the opt-in instead of pretending to provide cross-UID pass-through.  If the input service/value is unavailable, it fails with `PASS_THROUGH_UNSUPPORTED`.

This admission check is deliberately narrower than a delivery guarantee: the library cannot account for raw `WindowManager` overlays made by the same app outside this manager, the target app may hide application overlays, and the platform remains authoritative.  On API 23--30 the explicit option is accepted but is documented as platform-dependent rather than guaranteed.  T06 must test the calculation (including multiple handles) and a cross-UID target with Android instrumentation on either an emulator or physical device; physical hardware is useful additional coverage, not a release gate.

### Result, state, and retry semantics

The following is the complete handle state machine.  A handle accepts a `View` with no parent at factory creation.  While `ATTACHED`, its parent must be the library window owned by that same handle; an externally-parented view is rejected with `ALREADY_HAS_PARENT`.  A caller must not attach, detach, or reparent the managed view itself.

| Call / pre-state | Success | Recoverable failure | No-op |
| --- | --- | --- | --- |
| `show`, CONFIGURED | `addView` returns -> registered `ATTACHED`, `changed=true` | remains `CONFIGURED`, result has failure | — |
| `show`, ATTACHED | — | — | success, `ATTACHED`, `changed=false` |
| `update(spec)`, ATTACHED | layout update succeeds -> `ATTACHED`, `changed=true` | remains `ATTACHED`; last successfully applied effective spec remains in effect | equal to the effective spec -> success, `changed=false` |
| `update(spec)`, CONFIGURED | replace pending spec -> `CONFIGURED`, `changed=true` | validation error throws | equal to the effective spec -> success, `changed=false` |
| `hide`, ATTACHED | remove succeeds -> `CONFIGURED`, `changed=true` | other remove failure remains `ATTACHED` so caller can retry | `NOT_ATTACHED` reconciles to `CONFIGURED`, successful no-op, retaining the `NOT_ATTACHED` diagnostic |
| `hide`, CONFIGURED | — | — | success, `CONFIGURED`, `changed=false` (retaining an existing diagnostic) |
| `dispose`, CONFIGURED | release references/listeners -> `DISPOSED`, `changed=true` (retaining an existing diagnostic) | — | — |
| `dispose`, ATTACHED | remove then release -> `DISPOSED`, `changed=true` | other remove failure remains `ATTACHED`; caller must retry | `NOT_ATTACHED` reconciles then releases -> `DISPOSED`, retaining the diagnostic |
| `dispose`, DISPOSED | — | — | success, `DISPOSED`, `changed=false`, retaining any existing diagnostic |

`ATTACHED` means that the latest library `WindowManager.addView`/replacement call returned successfully and has not subsequently been reconciled as detached.  It is not a promise that pixels have been rendered, that `View.onAttachedToWindow` has already run, or that the overlay remains visible after a later platform/policy change.  `getState()` and `getLastFailure()` are thread-safe and readable in every state, including `DISPOSED`; `getSpec()` is main-thread-only but readable there in every state, including `DISPOSED`.  After disposal, `getSpec()` returns the final effective immutable value, not a Context-, View-, Activity-, listener-, `WindowManager`-, or `Throwable`-retaining object.  `lastFailure` is cleared by the next ordinary successful direct operation.  A successful `NOT_ATTACHED` reconciliation through `hide()` (no-op) or `dispose()` (release), and a repeated `dispose()` after forced Activity cleanup, preserves the `NOT_ATTACHED` or forced-cleanup diagnostic; it remains observable until a later ordinary successful direct call (or forever when disposal is terminal).  `lastFailure` is set by the latest failed operation; the forced Activity-destruction failure is retained because no later window operation is valid.  `OverlayResult.cause` is nullable even when `failure` is non-null: preflight classifications such as permission, opacity-budget, or not-attached reconciliation can have no platform exception, while a caught platform exception is supplied only on that returned result for diagnostics.  `getView()` throws in `DISPOSED`, and disposal clears all library references to the View, Activity, listeners, and `WindowManager`; retaining the `OverlayView` object therefore cannot retain them.  `dispose()` is deliberately not `Closeable.close()`: a result is required so that removal failure cannot be silently lost.  The application owner must call it when the overlay's feature ends, and may retry a failed disposal while the handle remains `ATTACHED`.

Activity destruction has a distinct terminal path.  On `onDestroy`, the library attempts one immediate remove.  It then clears every handle reference and transitions to `DISPOSED` regardless of the remove outcome, because retrying an Activity-owned window after its owner is destroyed is invalid.  If removal throws, `getLastFailure()` becomes the classified failure and the exception is logged only for diagnostics; `DISPOSED` in this path means **library ownership and references are released**, not proof that the platform removal succeeded.  A retained handle cannot attach again, and the design makes no claim that an unverified framework attachment was removed.

An `update` which would require a platform window-type change follows explicit remove/add semantics: remove success then add success yields `ATTACHED`; if the add fails it yields `CONFIGURED` and reports the add failure.  The implementation must not report `ATTACHED` after a failed re-add.  This case should be rare because scope and touch mode define a stable type, but it is specified to avoid an undefined half-state.

### External detach and permission reconciliation

The handle registers an internal `OnAttachStateChangeListener` while it owns the View.  A main-thread `onViewDetachedFromWindow` that was not caused by a successful library removal reconciles `ATTACHED` to `CONFIGURED`, records `NOT_ATTACHED` until a later ordinary successful direct operation clears it, and makes a later explicit `show()` a new registration attempt.  This callback is a later observation, not proof that a successful `show()` rendered pixels synchronously.

The next `update`, `hide`, or `dispose` also classifies a framework `not attached` remove/update failure as `NOT_ATTACHED`: `hide` then returns successful `CONFIGURED`/`changed=false` and `dispose` releases the handle with successful `DISPOSED`, while both retain that diagnostic.  If the listener already reconciled the handle, an already-configured `hide` is the same successful no-op and an already-configured `dispose` releases successfully, also preserving the diagnostic.  Thus `NOT_ATTACHED` is a reconciliation outcome, never a stuck `ATTACHED` state; an already-disposed `dispose` remains successful with `changed=false` and preserves any existing diagnostic, including forced Activity-cleanup failure.  Any other update/remove failure leaves `ATTACHED`, because the library cannot infer whether the framework retained the window.  Application overlay permission can be revoked or platform policy can hide/remove a window after registration: the library does not claim continuous visibility, and a failed later operation returns its classified failure.  Once a detach is observed/reconciled, the owner rechecks permission and explicitly calls `show()` after restoring the condition; there is no background watcher or automatic re-add.

There is no automatic retry, exponential backoff, or hidden permission watcher.  `PERMISSION_DENIED`, a temporarily invalid activity token, and a transient framework rejection are reported immediately; after the app fixes the condition, it invokes `show`, `update`, `hide`, or `dispose` again on main.  `OverlayResult.cause` contains a caught platform exception only when one exists; clients branch on `OverlayFailure`, not exception message text.

## Permission and lifetime boundary

`OverlayPermission` is an immutable, thread-safe helper:

```kotlin
class OverlayPermission {
    fun isGranted(context: Context): Boolean
    fun settingsIntent(context: Context): Intent
}
```

For API 23+ `isGranted` delegates to `Settings.canDrawOverlays`; below the chosen minimum it has no behavior because 3.0 will not support that range.  `settingsIntent` is a plain `ACTION_MANAGE_OVERLAY_PERMISSION` intent for the caller's package; it does not start an activity and has no Fragment/Dialog dependency.  The host launches it from a visible Activity using its usual Activity Result API, rechecks permission on return, then calls `show()` itself.  `showPermissionRequestDialog` and `requestOverlayPermission` are removed: a library cannot supply an application's rationale, lifecycle, or navigation policy.

The application-scoped `newOverlayView(view, spec)` requires overlay permission for every `show`, including pass-through windows.  It reports `PERMISSION_DENIED` before calling `WindowManager` if absent.  The activity-scoped `newOverlayView(view, activity, spec)` never checks or requires `SYSTEM_ALERT_WINDOW`; it is bounded by the supplied Activity window and is disposed at that Activity's destruction.  Factory creation rejects a finishing/destroyed activity.  Activity recreation requires a new handle and a new view; implicit reattachment to the replacement Activity is prohibited.

## Kotlin migration boundary

The proposed implementation boundary is intentional rather than a mechanical conversion:

* T04--T06 and T08 may implement the state machine, main-thread checker, window adapter, immutable spec, and activity lifecycle cleanup in Kotlin.  Their public classes must use explicit visibility, AndroidX nullability annotations where needed, `@JvmStatic`, explicit manually-written Java overloads for both factory shapes (with and without `OverlaySpec`), and Java-friendly bean getters (`getState`, `getView`, `getSpec`, `isSuccess`).  `@JvmOverloads` is only appropriate for non-ambiguous constructors; Kotlin default arguments do not replace these factory overloads.
* Keep the public runtime API JVM-first: no suspend functions, Flow, Kotlin `Result`, inline/value classes, default-interface-method requirements, or Kotlin-only collection types.  Java and Kotlin compilation tests are mandatory for every public signature added or changed.
* `DraggableOnTouchListener` becomes internal (or is deleted) with no replacement hook in 3.0.  The drag behavior belongs to the handle contract, which lets T05/T06 correct coordinate and touch behavior without exposing internal state.
* T07 owns opt-timber.  `DebugOverlayTree` may be converted to Kotlin only in its own mechanical commit, retaining `DebugOverlayTree.init(Application)`, Java-accessible setters, and a new explicit `dispose()` that unregisters lifecycle callbacks.  Its `log` entry point remains safe from any thread through a locked bounded deque plus one posted main render.
* T09 owns lint.  It must update the detector to the final 3.0 symbol(s) or remove this policy rule when `allowViewToExtendOutsideScreen` is removed; it must not retain a detector that matches unrelated same-named methods.

## Public-name compatibility decision

| Option | Benefit | Cost / risk | T01 recommendation |
| --- | --- | --- | --- |
| Keep `OverlayViewManager`, `OverlayView`, and both `newOverlayView` factory shapes; introduce immutable `OverlaySpec` and result-returning window operations | Existing imports, conceptual model, and most factory call sites survive; T04--T08 can focus on reliability instead of a package-wide rename | Fluent mutable setters and chained `show()` must change because their old success/ordering semantics are unsafe | **Adopt** |
| Rename to `OverlayManager` / `OverlayHandle` | Names distinguish manager and resource ownership more directly | Breaks every user import and lint/document/sample reference without fixing a lifecycle or threading defect | Reject for 3.0 |

This is intentionally a minimum-breaking architecture: retain names where they carry no correctness cost, but make the necessary behavioral break at mutable layout state and `show`/`hide`/`update`/`dispose` results.  A deprecated compatibility shim is not proposed because a fluent setter that appears synchronous while changing a later window operation would reintroduce the ambiguity that 3.0 is intended to remove.

## 2.x breaking changes and migration examples

| 2.x | 3.0 replacement / reason |
| --- | --- |
| `OverlayViewManager.init()` then global `getInstance()` | Same names remain; initialization is idempotent for the same application and rejects a different application. |
| `newOverlayView(view)` | Same factory name remains and accepts an immutable `OverlaySpec`; owner retains and disposes the returned `OverlayView`. |
| `newOverlayView(view, activity)` | Same activity factory name remains and accepts `OverlaySpec`; it is destroyed with that Activity. |
| Fluent mutable setters and `show()` returning `OverlayView` | Build immutable `OverlaySpec`, call `show()` and inspect `OverlayResult`; use `update(newSpec)` for a changed layout. |
| `isVisible()` | `getState() == OverlayState.ATTACHED`; it means the latest registration succeeded and has not been reconciled as detached, not that pixels are currently rendered. |
| `OverlayView.setOnClickListener(listener)` | Call `view.setOnClickListener(listener)` on the supplied View, on main before disposal; `OverlayView` no longer forwards a click-listener setter. |
| Permission dialog/launcher methods | host owns rationale and Activity Result; call `overlayPermission().settingsIntent()` and recheck. |
| `allowViewToExtendOutsideScreen(true)` | no direct replacement.  In the observed 2.x implementation, a touchable pre-O overlay selected privileged `TYPE_SYSTEM_ERROR`; 3.0 never selects it.  Constrain UI using `WindowInsets` and explicitly design platform/system-bar behavior. |
| Custom `DraggableOnTouchListener` | no public replacement; use `DRAGGABLE` or implement an app-owned overlay interaction. |
| `getDisplayWidth/Height()` | host obtains bounds/insets for its target window; display-wide pixel values are ambiguous in multi-window. |
| `getX()` / `getY()` | `getSpec().getX()` / `getSpec().getY()` (Kotlin: `spec.x` / `spec.y`) on the main thread; these are fields of the effective immutable specification. |
| `setScreenBrightness(...)` | Set `OverlaySpec.screenBrightness` only for an activity-scoped factory; application-scoped overlays do not support a brightness override. |
| Background-thread calls that 2.x posted or queued | 3.0 throws before any window operation because handle creation and mutation are main-thread-only; post the call to the main executor from the host application. |

Kotlin migration:

```kotlin
OverlayViewManager.init(application)
val view = TextView(activity).apply {
    setOnClickListener { /* ordinary click delivery remains available with DRAGGABLE */ }
}
val overlay = OverlayViewManager.getInstance().newOverlayView(
    view,
    activity,
    OverlaySpec(touchMode = OverlayTouchMode.DRAGGABLE)
)
check(overlay.show().isSuccess)
// Preserve the effective values and change only the requested fields.
overlay.update(overlay.spec.copy(x = 24, y = 48))
```

Java application-overlay migration, including a permission retry owned by the app:

```java
OverlayPermission permission = manager.overlayPermission();
if (!permission.isGranted(activity)) {
    permissionLauncher.launch(permission.settingsIntent(activity));
    return;
}
OverlayResult shown = overlay.show();
if (!shown.isSuccess() && shown.getFailure() == OverlayFailure.PERMISSION_DENIED) {
    // Permission may have been revoked between the check and show; do not auto-retry.
}
// A worker-thread caller migrates every handle operation by posting it to main.
new Handler(Looper.getMainLooper()).post(() -> {
    // Java partial update starts with the effective specification.
    OverlayResult updated = overlay.update(
            overlay.getSpec().toBuilder().setAlpha(0.75f).build());
    OverlayResult disposed = overlay.dispose();
    // Inspect updated/disposed on main if the owner needs recovery logic.
});
```

## Acceptance contract for follow-on tasks

### T04 — state and thread processing

* Test non-main public mutators fail before a `WindowManager` call; no posted operation remains to run later.
* Test add failure leaves `CONFIGURED`, `isSuccess == false`, a classified failure and nullable diagnostic cause, and permits an explicit show retry after permission is granted.
* Test preflight failures can return a non-null `OverlayFailure` with a null `cause`; a caught platform exception is exposed only by that result and is not retained by the handle.
* Test worker-show/main-hide cannot reorder; repeated show/hide/update no-ops and each state/result pair above are covered.
* Test update failure preserves attached state and last applied layout; remove/re-add failure never falsely reports attachment.

### T05 — monitoring, coordinates, and permission boundary

* Activity draggable overlay attaches with `SYSTEM_ALERT_WINDOW` denied and creates no application monitor window.
* No `ScreenMonitor`-style auxiliary application window exists; bounds are recomputed for rotation, RTL, insets, and multi-window as specified.
* Permission settings return path tests denied -> grant -> explicit `show()` retry and grant -> revoke -> failed update/show.

### T06 — touch and drag behavior

* Cover DOWN/MOVE/UP/CANCEL, touch slop click-versus-drag, multi-pointer active-pointer changes, alpha restoration, and off-screen/bounds behavior.
* Verify a completed drag updates `getSpec().getX()`/`getY()`, equality is against that effective spec, Kotlin `copy` and Java `toBuilder` preserve unspecified values, and every touch mode remains `FLAG_NOT_FOCUSABLE`.
* Verify `SAME_UID_ONLY` and explicit cross-UID behavior against a different-UID target on Android 12+; calculate the conservative combined opacity for one and multiple library handles, reject over-budget requests, and accept emulator instrumentation as valid evidence.
* Cover API 26, API 35 edge-to-edge, and the documented system-bar limitation; no legacy privileged window type is selected.

### T07 — Timber safety

* Logging from multiple worker threads cannot mutate `TextView` off-main or corrupt the buffer.  Rendering is coalesced, preserves ordered bounded output, and validates `maxLines`: values below 1 throw `IllegalArgumentException`, shrinking trims immediately, and a zero-length output is never passed through `setLength(-1)`.
* Activity registration/lifecycle and `dispose()` release all callbacks and overlay resources; Java API compatibility tests cover the public tree methods.

### T08 — initialization and release

* Same-application initialization is idempotent; a different application is rejected without replacing live state.
* Activity destruction attempts removal, then disposes handles/listeners and leaves no retained activity path even when removal fails.  Verify the `WeakHashMap` concern with a reference-path or heap test, not assertion by weak key alone; assert the forced-disposal diagnostic rather than claiming framework detachment after a failed remove.
* Application overlays require explicit successful `dispose`; a failed removal remains retryable/attached and is reported.  Repeated initialization never leaves an old monitor/window/listener.

### T09 — lint and packaging

* Update/remove the obsolete outside-screen detector based on the approved public API; test Java and Kotlin callers plus an unrelated same-named method.
* Publish lint in the AAR and validate it from a separate consumer.  Its rule text must not claim system-bar access that 3.0 does not provide.

## Choices requiring bilateral coordinator approval

1. Adopt immutable `OverlaySpec` and result-returning window operations while retaining the established `OverlayViewManager` / `OverlayView` names and factory shapes.
2. Adopt the strict main-thread contract and explicit `OverlayResult`, including no library async queue or automatic retry.
3. Adopt recommended `minSdk 23`; otherwise record the API 21--22 support/testing obligation and permission/type behavior.
4. Confirm whether an application overlay must offer screen-brightness configuration.  This proposal disallows it (activity scope only) because screen brightness is window- and UX-sensitive.
5. Confirm the exact AGP 9.2.x/Kotlin plugin patch only after T03's clean compatibility validation.
